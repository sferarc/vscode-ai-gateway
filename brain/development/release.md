# Release

`.github/workflows/release.yml` runs only when the repository variable `RELEASE_ENABLED` is `true` ([[decisions/2026-10-08-release-gated-on-variable]]). It was set to `true` on 2026-10-20 after the publish path was checked (below). Do not tag, publish or bump the version by hand; the version pull request and the workflow do it. Setting or clearing the variable stays the owner's step. The workflow arms auto-merge on the version pull request, so it lands on the required checks alone and nobody merges it by hand ([[decisions/2026-11-06-version-packages-auto-lands]], which superseded [[decisions/2026-10-21-agents-merge-version-packages]]).

## The flow

The job runs only when `github.ref` is `refs/heads/main` as well as `RELEASE_ENABLED` is `true`, so a manual dispatch from any other branch skips it instead of publishing that branch with `VSCE_PAT` (#208, part of sferarc/hq#912). It runs in the `release` environment. The sferarc-hq App cannot create environments (HTTP 403, no Administration write, sferarc/hq#888), so GitHub creates `release` on the first run with no deployment branch policy, and the `github.ref` guard is the only control until #209 restricts it to `main`. `src/release-workflow.test.ts` checks the guard and the environment.

On a push to `main` (or a manual dispatch from `main`), `changesets/action`:

- with pending changesets in `.changeset/`, opens or updates a "Version Packages" pull request that bumps `package.json` and writes `CHANGELOG.md`;
- with none, runs `pnpm release`, which is `scripts/release.sh`.

`scripts/release.sh` compares `package.json` `version` with what the Marketplace has for `SferaDev.vscode-extension-vercel-ai` (`vsce show`). If they match it exits; otherwise it runs `pnpm package` and `vsce publish --no-dependencies --packagePath ./*.vsix`, treating "already exists" as success because a concurrent run may have published first.

Secrets the workflow reads: the organization secrets `HQ_APP_ID` and `HQ_APP_PRIVATE_KEY`, from which `actions/create-github-app-token` mints a sferarc-hq App token scoped to this repository, and `VSCE_PAT` on the repository for the Marketplace. The App token is what `changesets/action` and the release step use, so the version pull request and its branch push trigger the `pull_request` workflows behind the required checks (those made by the Actions token trigger none) and are authored by sferarc-hq[bot]. It replaced the `GIT_TOKEN` organization secret, a personal token whose commits and pull requests were authored by the owner. Both organization secrets have `selected` visibility, so this repository must be in their repository list or the mint step fails and nothing releases. The package is `private` in `package.json` and nothing goes to npm (the workflow comment). Open VSX is not published to.

Before `changesets/action` runs, the step "Skip when the branch has moved on" (`id: head`) reads the current head of the run's ref with `git ls-remote --exit-code origin $GITHUB_REF`. When it is not `GITHUB_SHA`, the step writes a notice and sets `current=false`, and both the version or publish step and the tag step are skipped; the run on the newer commit does the work. If the head cannot be read the job fails. The workflow's `concurrency` group serializes runs but each still works from its own checkout, so without the check a run on a superseded commit reopened the version pull request for 0.5.4 after #78 had already published it (#81, #82, issue #124). The check runs after `pnpm install`, so a push landing in the seconds between the check and `changesets/action` is not caught. `src/release-workflow.test.ts` runs the step's script against a stub `git`.

`.changeset/config.json` versions private packages and does not tag them (`privatePackages.tag: false`), so `changesets/action` creates no tag or release. A final workflow step runs `scripts/github-release.sh`: it skips when the release `v<package.json version>` exists, creates the release from the tag with `--verify-tag` when only the tag exists, and otherwise runs `gh release create --target $GITHUB_SHA`, which also creates the tag, so reruns and dispatches are idempotent. Only an HTTP 404 counts as absent; any other lookup error fails the step. Before that script the step used `gh release view` with its errors discarded, so on run 41495924331 (`5a50a3f`, 2026-11-02) a failed lookup was read as no release and the create got HTTP 422 `Release.tag_name already exists` for `v0.5.22`, which had shipped at 11:00; the sferarc-hq App installation's API budget read 0 remaining shortly after, so a rate limit is the likely cause, though the discarded error cannot confirm it. `src/github-release.test.ts` runs the script against a fake `gh`. Both steps use the App token. The tag step is limited to `main` and gated on the action's `has-changesets` output, which is kebab-case (`index.ts` in `changesets/action` v2.1.2 sets `has-changesets`); `hasChangesets` is not an output, evaluates empty and skips the step on every run. If publishing succeeds and the tag step fails, the next push tags a later commit than the one that shipped.

`CHANGELOG.md` is shipped in the VSIX (not in `.vscodeignore`) so the Marketplace shows it.

## Current state

`SferaDev.vscode-extension-vercel-ai` `0.5.0` was published by the run on Version Packages #48 (39556789195), which proves `VSCE_PAT`. The version pull request lands on the required checks alone: the step "Enable auto-merge on the version PR" runs `gh pr merge --squash --auto` with the App token on the action's `pr-number` output whenever the action created or updated it, so it merges once the required checks on `main` pass: `Check`, `Approved stack` and `No Claude attribution` ([[ci]]). Before that step a steward merged each one by hand. The output is kebab-case in v2.1.2 (`action.yml`); v1's `pullRequestNumber` would evaluate empty and skip the step, and `src/release-workflow.test.ts` guards the spelling. The tag step runs only when `changesets/action` reports no pending changesets, so a push that opens or updates a version PR never tags. `v0.5.0` was created once by hand at `a0c487a`, the commit that shipped. `0.5.1` (Version Packages #56) and `0.5.2` (#59, `c722a91`) were published without a tag or release because the step read `hasChangesets`, so it was skipped (runs 39636897330 and 39688604271); `src/release-workflow.test.ts` guards the spelling. Since the fix (#60) merged, a push to `main` with no pending changesets tags and releases the `package.json` version at that commit, so it would not tag `v0.5.1` or `v0.5.2`. Both were backfilled by hand on 2026-10-22: `v0.5.1` at `12053e9` and `v0.5.2` at `c722a91`, each with a release ([[decisions/2026-10-22-backfill-release-tags]]). The patch changeset `.changeset/tag-release-after-publish.md` keeps `has-changesets` true on the fix's own merge push, so nothing is tagged at that commit, which never shipped; the first tag the workflow created is `v0.5.3`, at the Version Packages merge commit 49d3afd (#62), and that release is the one marked Latest because the backfilled releases were not. Without it `scripts/release.sh` would skip as already published and the step would tag `v0.5.2` at the wrong commit, so keep it.

Seven more Version Packages pull requests merged between 2026-10-27 and 2026-10-28, from #78 (`0.5.4`, `40e1239`) to #103 (`0.5.10`, `d221cdb`), each carrying the patch changesets merged before it (`CHANGELOG.md`). Whether each version reached the Marketplace and got its tag was not checked for this note.

To add a release note to a change, run `pnpm changeset` and commit the file it writes.
