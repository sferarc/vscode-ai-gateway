# Configuration

Seven settings, declared in `package.json` `contributes.configuration` and read by `getConfig()` in `src/config.ts` on every call, so a change applies to the next request without a reload:

| Setting | Default | Used by |
| --- | --- | --- |
| `vercelAiGateway.endpoint` | `https://ai-gateway.vercel.sh` | model list (`{endpoint}/v1/models`) and chat (`{endpoint}/v1/ai`); `getConfig()` trims spaces and strips trailing slashes, so both URLs come from one normalised value, and uses the default when the result is empty or the value is not a string (`normalisedEndpoint`). The Settings editor saves a cleared field as `""`, which used to build the relative URL `/v1/models`, and a number in `settings.json` made `getConfig()` throw on `replace` for every request. A trailing `/v<number>` or `/v<number>/ai`, any case, is then dropped (`API_VERSION_SUFFIX`), since Vercel's docs give `https://ai-gateway.vercel.sh/v1` as the OpenAI SDK base URL ("OpenAI Chat Completions API with AI Gateway", checked 2026-11-01) and `@ai-sdk/gateway` documents `https://ai-gateway.vercel.sh/v4/ai` as its default `baseURL`, and either pasted here built `/v1/v1/models` or `/v4/ai/v1/models`, which the public gateway answered with 404 on 2026-11-01 (`/v1/models` answered 200). A longer path such as `/v1/proxy` or `/v1beta` is kept. Tests: "falls back to the default endpoint", "drops the API version" and "keeps a path that is not a bare API version" cases in `src/config.test.ts`. Declared `"scope": "machine"` and read as `inspect("endpoint")?.globalValue`, so only the user's own setting counts and a workspace or folder value is ignored ([[decisions/2026-10-15-endpoint-user-settings-only]]) |
| `vercelAiGateway.timeout` | `30000` ms, range 5000 to 300000 | idle limit for the model's first chunk and for each next chunk (`firstChunkMs` and `chunkMs` in the `streamText` timeout, since #8), not a cap on the whole response; also the total limit for the model list request, the Check Connection request and the check of a new API key ([[authentication]]). VS Code returns a `settings.json` value outside the manifest's type or range as is and only underlines it, so `getConfig()` clamps a number to 5000 to 300000 (`MIN_TIMEOUT_MS` and `MAX_TIMEOUT_MS`) and uses the default for anything that is not a finite number. Before that, `0` timed out every model list fetch at once and a string made `AbortSignal.timeout` in Check Connection throw |
| `vercelAiGateway.disallowPromptTraining` | `false` | chat requests (#133): when on, `provideLanguageModelChatResponse` sends `providerOptions: { gateway: { disallowPromptTraining: true } }`, merged with `caching: "auto"` when the request carries a cache breakpoint (`gatewayOptions` in `src/provider.ts`, [[chat-provider]]). Vercel's "AI Gateway Disallow Prompt Training" docs (checked 2026-11-02) say the option is free for every gateway user, routes only to providers that do not train on prompts (fallbacks included), is not enforced for BYOK requests, and answers HTTP 400 with the flat body `{ "error": "<message>", "type": "no_providers_available" }` when no provider qualifies. `@ai-sdk/gateway` 4.0.126 cannot parse that flat body and replaces the message with "Invalid error response format", so `describeGatewayError` reads the type and message from the raw response (`noProvidersAvailable` in `src/errors.ts`) and tells the user to pick another model or turn the setting off; it accepts the nested `{ error: { message, type } }` shape too, since which one the live gateway sends is untested. `getConfig()` reads it with `inspect` and counts it on when the user, workspace or folder value is `true`, so a workspace can turn the filter on but not off over the user's choice. Tests: "getConfig disallowPromptTraining" in `src/config.test.ts`, the prompt training cases under `provideLanguageModelChatResponse` in `src/provider.test.ts`, and the "no provider that disallows prompt training" cases in `src/errors.test.ts` |
| `vercelAiGateway.zeroDataRetention` | `false` | chat requests (#137): when on, `provideLanguageModelChatResponse` sends `providerOptions: { gateway: { zeroDataRetention: true } }`, merged with the caching and prompt training options (`gatewayOptions` in `src/provider.ts`). Vercel's "AI Gateway Zero Data Retention (ZDR)" docs (checked 2026-11-02) say per-request ZDR costs nothing extra but is only available on Pro and Enterprise, that it is a superset of disallowing prompt training, that BYOK keys are skipped unless marked as ZDR in the dashboard, that fallbacks are filtered too, and that a model with no ZDR provider fails with the same flat `no_providers_available` body as the prompt training filter, so `describeGatewayError` names both settings in that message. What the gateway answers a Hobby team that sends the option is unknown. Read with `inspect` like `disallowPromptTraining`: a workspace can turn it on but not off. Tests: "getConfig zeroDataRetention" in `src/config.test.ts`, the zero data retention cases under `provideLanguageModelChatResponse` in `src/provider.test.ts`, and "names a model with no provider that offers zero data retention" in `src/errors.test.ts` |
| `vercelAiGateway.providerSort` | `default` | chat requests (#140): `cost`, `ttft` or `tps` is sent as `providerOptions: { gateway: { sort } }`, merged with the other gateway options (`gatewayOptions` in `src/provider.ts`). The "Provider sorting" section of Vercel's "AI Gateway Provider Filtering, Ordering, and Sorting" docs (checked 2026-11-02) says the gateway ranks the providers serving the model by estimated cost, median time to first token or median tokens per second, tries them in that order and falls back through the rest, gives degraded providers a penalty and puts down ones last, and reports the ranking in `providerMetadata.gateway.routing.sort`, which the extension does not read. It filters no provider, so it cannot add a `no_providers_available` failure, and the docs name no extra cost or plan requirement for it. `default` sends nothing and keeps the gateway's ranking by recent uptime and latency. `getConfig()` reads it with `get`, so a workspace value overrides the user's: it only reorders providers that already serve the model, unlike the data policy filters a workspace may not turn off. Any value outside the manifest's enum, including another case, is treated as `default` (`providerSort` in `src/config.ts`). Tests: "getConfig providerSort" in `src/config.test.ts` and the provider sort cases under `provideLanguageModelChatResponse` in `src/provider.test.ts` |
| `vercelAiGateway.providerOrder` | `[]` | chat requests (#143): a non-empty list is sent as `providerOptions: { gateway: { order } }`, merged with the other gateway options (`gatewayOptions` in `src/provider.ts`). The "Provider ordering" section of Vercel's "AI Gateway Provider Filtering, Ordering, and Sorting" docs (checked 2026-11-02) says the gateway tries the listed provider slugs first and still falls back to the providers not listed; with `sort`, the listed providers go to the front and the rest follow the sorted order. The docs do not say what an unknown slug or one that does not serve the model does (unknown). `getConfig()` reads it with `get`, so a workspace value overrides the user's, for the same reason as `providerSort`: it excludes no provider. Non-array values give nothing; entries are trimmed and lowercased, and empty, non-string and repeated ones are dropped (`providerSlugs` in `src/config.ts`), since the docs list every slug in lowercase. Tests: "getConfig providerOrder" in `src/config.test.ts` and the provider order cases under `provideLanguageModelChatResponse` in `src/provider.test.ts` |
| `vercelAiGateway.providerOnly` | `[]` | chat requests (#153): a non-empty list is sent as `providerOptions: { gateway: { only } }`, merged with the other gateway options (`gatewayOptions` in `src/provider.ts`). The "Provider filtering" section of Vercel's "AI Gateway Provider Filtering, Ordering, and Sorting" docs (checked 2026-11-03) says `only` is a hard filter: the gateway routes only to the listed slugs and never falls back outside them, so the request fails when none serve the model or all are down or rate limited; `order` is applied inside the allowed set, `sort` ranks within it, and it does not stop a BYOK key from falling back to the gateway's system credentials. The docs say the failure names the allowed providers but give no status or body (unknown), so the extension only names the setting when the refusal is the 400 `no_providers_available` body the data policy filters use: `reportError` passes `request.providerOnly` to `describeGatewayError`, which then lists the slugs and tells the user to add a provider (`noProvidersMessage` in `src/errors.ts`). `getConfig()` reads only `inspect().globalValue`, like `endpoint`, and the manifest marks it `"scope": "application"`: a cloned repo's list could fail every request or move spend to another provider account. Entries go through `providerSlugs` like `providerOrder`. Tests: "getConfig providerOnly" in `src/config.test.ts`, the provider only cases under `provideLanguageModelChatResponse` in `src/provider.test.ts`, and "names the providerOnly setting" in `src/errors.test.ts` |

The model list cache is keyed by API key only, so a change to `endpoint` drops it: `VercelAIChatModelProvider` listens to `workspace.onDidChangeConfiguration` and, when `vercelAiGateway.endpoint` is affected, calls `invalidateCache` and fires `onDidChangeLanguageModelChatInformation`, the same refresh a session change triggers ([[chat-provider]]). Before that, the old endpoint's models stayed in the picker for up to 5 minutes, and a failing new endpoint fell back to the old endpoint's list. A `timeout` change does not refresh anything. Test: "invalidates cache and fires model info change when the endpoint setting changes" in `src/provider.test.ts`.

Constants that are not settings live in `src/constants.ts`: the models path, the 5 minute cache TTL, a 15 minute `TOKEN_REFRESH_MARGIN` (an OIDC token counts as expired that long before it expires, `isExpired` in `src/vercel-auth.ts`), a 15 second `VERCEL_API_TIMEOUT_MS` for each `api.vercel.com` request in the OIDC flow (fixed, unlike the `timeout` setting, which covers gateway requests), and the user-facing error strings.
