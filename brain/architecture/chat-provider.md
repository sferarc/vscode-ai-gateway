# Chat provider

`VercelAIChatModelProvider` in `src/provider.ts` implements VS Code's `LanguageModelChatProvider`.

## Model list

`provideLanguageModelChatInformation` gets a key from the active session ([[authentication]]) and returns `[]` without one, or when the fetch fails and there is no earlier list for that key to fall back on. `ModelsClient` (`src/models.ts`) calls `GET {endpoint}/v1/models` with a bearer token, keeps only models whose `type` is `chat`, `language` or absent, and maps them to `LanguageModelChatInformation`:

- `family` and `version` come from `parseModelIdentity` (`src/models/identity.ts`).
- `maxOutputTokens` is `max_tokens` capped at half of `context_window`, and `maxInputTokens` is the rest of the window, so a prompt VS Code fills to `maxInputTokens` still fits the default output limit. The gateway's `context_window` covers input and output together, and many models report `max_tokens` equal to it ([[decisions/2026-10-26-context-window-split]]). A missing or zero value passes through unchanged.
- A model with a positive `deprecated_at` gets `detail` "Vercel AI Gateway, deprecated YYYY-MM-DD" and the same date at the end of its `tooltip` (`deprecationDate` in `src/models.ts`). On 2026-10-27 the public list sent `deprecated_at` in milliseconds for six language models, with dates from 2026-10-31 to 2026-11-18, while `created` and `released` are in seconds, so a value below 10^12 is read as seconds. The models stay listed whatever the date; whether the gateway still serves one after its date is unknown. Test: "names the deprecation date of a model the gateway marks as deprecated" in `src/models.test.ts`.
- Image input, tool calling and reasoning are read from the gateway's structured fields, falling back to tags only when a field is absent (SferaDev/SferaDev#559). Web search is tags only, since no field exists.

The list is cached for 5 minutes (`MODELS_CACHE_TTL_MS`, `src/constants.ts`). Both the cache and the in-flight request are keyed by the API key they were fetched with: concurrent calls with the same key share one request, and a call with a different key starts its own and never sees another key's list. A failed fetch is not cached. When a refresh fails and the cache still holds a list fetched with the same key in the current generation, expired or not, `getModels` returns that list and logs a warning with the time it was fetched, so a network blip does not empty the model picker. The request, body included, is aborted after the `timeout` setting ([[configuration]]) and fails with "Timed out after N ms waiting for {url}", so a gateway that never answers cannot leave the in-flight request pending. Any session change on the `vercelAiGateway` provider calls `invalidateCache` and fires `onDidChangeLanguageModelChatInformation` (SferaDev/SferaDev#344), and so does a change to the `endpoint` setting, since the cache key does not include the endpoint ([[configuration]]). `invalidateCache` drops the cache and the in-flight request and bumps a generation counter so a fetch started before the switch cannot write its result into the cache when it lands. The `models cache` tests in `src/models.test.ts` cover sharing, expiry, failures, the stale fallback, the timeout, invalidation during a fetch and a key change during a fetch.

A failed fetch throws `ModelsFetchError` with the status when there was one. Its message names the URL and the status, plus the gateway's `error.message` from a JSON body or the raw body cut to 500 characters; a reply that is not JSON or has no `data` array fails the same way instead of yielding an empty or undefined list (#21). `provideLanguageModelChatInformation` logs every failure, and on a non-silent call also shows an error message with "Show Logs", plus "Manage Authentication" first for a 401 or 403. Silent calls show nothing. Tests: `fetch failures` in `src/models.test.ts` and `model list failures` in `src/provider.test.ts`.

## Getting a key

`getApiKey` is the only place a model-list or chat request gets credentials. It reads the active session from this extension's own provider ([[decisions/2026-08-09-active-session-from-own-provider]]) and falls back to `authentication.getSession` with `createIfNone` only when there is no session and the request may prompt. Without a key the model list is `[]` with no fetch, and a chat request reports `**Error:** Not signed in to Vercel AI Gateway.` in the chat, naming the "Vercel AI Gateway: Manage Authentication" command and both sign-in methods, without building a gateway provider (`ERROR_MESSAGES.NOT_SIGNED_IN` in `src/constants.ts`). It used to say "Vercel AI Gateway API key not found", which named no next step and read as wrong to an OIDC user. Test: "tells a signed-out chat to run Manage Authentication and makes no gateway request" in `src/provider.test.ts`.

| Situation | Silent | Prompting |
| --- | --- | --- |
| Reading the active session throws | No key, nothing logged or shown | Error logged, `AUTH_FAILED` toast |
| No session | No key, sign-in not started | Sign-in started |
| User cancels sign-in | Not reached | Logged at info, no toast |
| Sign-in fails otherwise | Not reached | Error logged, `AUTH_FAILED` toast |
| Sign-in resolves no session | Not reached | No key, no toast |

A cancel is recognised by what VS Code rejects with: `User did not consent to login.` when the consent prompt is dismissed, or an error named `Canceled` (`mainThreadAuthentication.ts` in the VS Code repository). Dismissing a picker inside this extension's own `createSession` (`src/auth.ts`) throws `AuthCancelledError` ([[authentication]]), which `isSignInCancellation` also recognises by name, so it is logged at info like the others. Whether an error's name survives the trip through VS Code's `authentication.getSession` is unknown, so this holds only if the name survives. An attempt to settle it in the extension host test (`e2e/suite.cjs`, VS Code 1.137.0) failed; the experiment code was never committed, so this is unrecorded beyond this note: `getSession(..., { createIfNone: true })` rejected with `DialogService: refused to show dialog in tests` for the "wants to sign in" consent, before `createSession` ran, and a patched `trustedExtensionAuthAccess` in `product.json` did not skip it. The picker was never reached headlessly; the unit test in `src/provider.test.ts` rejects with a plain `Error` carrying that name to match. No log line on these paths carries the token. Covered by the `sign-in fallback` tests in `src/provider.test.ts`.

## Chat requests

`provideLanguageModelChatResponse` builds an AI SDK gateway provider (`createGatewayProvider` from `@ai-sdk/gateway`) with the session's token and `baseURL` `{endpoint}/v1/ai`, then streams with `streamText` from `ai`. `modelOptions.temperature` and `modelOptions.maxOutputTokens` are passed through when VS Code sets them, except that a temperature is dropped, with a debug log, for a model the last fetched list marks as taking none (`ModelsClient.acceptsTemperature`). The gateway's `temperature` flag decides, then whether `supported_parameters` lists `temperature`, and a model with neither, or one not in the list, accepts it. On 2026-10-26 the public `/v1/models` list had 39 language models with `temperature: false`, among them OpenAI's `o` and `gpt-5` series and recent Anthropic models, and none of them listed `temperature` in `supported_parameters`. Whether the gateway rejects or ignores a temperature sent to them is untested. Otherwise temperature is left to the provider. `maxOutputTokens` is the model's own `maxOutputTokens` when positive and unset when not, and a caller's `modelOptions.maxOutputTokens` replaces it only when it is a finite number of at least 1 after rounding down (the AI SDK rejects anything else with `maxOutputTokens must be an integer` or `must be >= 1`) and no higher than the model's own; a higher one is lowered to the model's with a debug log (`outputTokenLimit` in `src/provider.ts`), since the model's limit is what keeps a prompt filled to `maxInputTokens` inside the context window ([[decisions/2026-10-26-context-window-split]]). With no model limit the caller's value passes through. Tests: the output limit cases under `provideLanguageModelChatResponse` in `src/provider.test.ts`. The `timeout` setting ([[configuration]]) is an idle limit, not a cap on the whole request: it is passed as both `firstChunkMs` and `chunkMs`, so it bounds the wait for the first chunk and the gap between any two chunks, and a long answer that keeps streaming is never cut off (#8). When it fires, `streamText` ends `fullStream` with an `abort` part instead of throwing; the loop treats that part, or a thrown `AbortError` or `TimeoutError`, as a timeout and reports "Request timed out after N ms with no output from the model." (#12). Cancellation aborts the stream through an `AbortController`, and a stream that ends because the user cancelled reports nothing.

`convertMessages` splits VS Code's messages into `messages` and `instructions`. VS Code sends its system prompt as assistant messages before the first user message; those go to the `instructions` option because the AI SDK rejects `system` messages inside `messages` ([[decisions/2026-08-09-system-prompt-as-instructions]]).

Each VS Code message becomes at most one assistant message and one tool message. An assistant message keeps its text and every tool call in their original order, and all tool results in a message share one `tool` message, since OpenAI-style APIs reject an assistant message with tool calls that is not followed directly by the results for each call. Tool results precede any user text sent alongside them. Every tool result part produces a result so no call is left without one: text and JSON or other textual data parts become text, joined with no separator; image data parts become `file` content; anything else becomes the placeholder `[Unsupported tool result content]`. `cache_control` data parts are skipped.

Data parts outside tool results follow the same rules: `cache_control` parts, VS Code's prompt cache breakpoints, are dropped, images become image content, textual MIME types are decoded to text, and any other type becomes `[Unsupported {mimeType} content]` with a warning logged. Before this, every non-image part was decoded as text, so each cache breakpoint appended the word `ephemeral` to its message and a binary attachment sent undecodable bytes. Tests: the `convertMessages` block in `src/provider.test.ts`.

Thinking parts (`LanguageModelThinkingPart`, a proposed API class looked up at runtime) are dropped from every message. The Copilot Chat extension's agent loop returns the thinking from earlier tool rounds of the same request in its assistant messages (`toolCalling.tsx` and `extChatEndpoint.ts` under `extensions/copilot` in the VS Code repository). A thinking part's `value` is a string or a string array, so a string one used to pass `isTextPart` and reach the model as assistant text. They are not sent as AI SDK `reasoning` parts because this extension's own thinking parts carry no id or signature, and how the gateway forwards unsigned reasoning to each provider is untested.

Errors, timeouts included, are reported into the chat as a `**Error:**` text part rather than thrown; a stream that ends with no content reports "No response received from model." A thrown error or an `error` stream part goes through `describeGatewayError` (`src/errors.ts`), which unwraps a `RetryError` to its last error and reads the status and retryability from the `GatewayError` and the URL from the `APICallError` the gateway provider keeps in its `cause`. 401 and 403 point the user to "Vercel AI Gateway: Manage Authentication", except a `GatewayForbiddenError` (the gateway's `forbidden` type, a routing or policy rule refusing the request, not a sign-in failure), which names the HTTP status and the rule id when the gateway sends one and says to check the team's AI Gateway rules or pick another model. For a `GatewayAuthenticationError` the `Details:` keep only the first line of its message plus the gateway's own message from the `APICallError` (`authenticationDetail` in `src/errors.ts`), because `GatewayAuthenticationError.createContextualError` in `@ai-sdk/gateway` replaces the gateway's message with setup steps for the SDK's `apiKey` option and the `AI_GATEWAY_API_KEY` variable, which the extension does not read. 429 says to wait, naming how long when the last attempt's response carries `retry-after-ms` or `retry-after` (seconds or an HTTP date), the headers the AI SDK's own retry delay reads (`getRetryDelayInMs` in `ai`), and "a moment" when neither gives a wait in the future (`retryAfterMs` in `src/errors.ts`). `streamText` retries a 429 twice before giving up, waiting what the headers ask when that is under 60 seconds, so the wait shown is the one the gateway asked for after the last retry. Whether the gateway sends either header on a 429 is unknown. Tests: the `rate limit wait` block in `src/errors.test.ts`. 5xx says the failure is usually temporary; the provider's own message follows as `Details:`. A `GatewayModelNotFoundError` (the gateway's `model_not_found`, HTTP 404) sets `modelNotFound`: the chat says to pick another model, and `reportError` drops the model cache and fires `onDidChangeLanguageModelChatInformation`, so a model the gateway stopped serving leaves the picker instead of staying until the 5 minute cache expires. A 404 of any other kind is reported as is. Each failure logs one line with model, status, URL without credentials or query, retryability and elapsed ms. The error object itself is not logged, because an `APICallError` carries the request body and headers. A `finish` part with reason `length` adds a note that the answer was cut off at the model's output token limit, and one with reason `content-filter` adds a note that the provider's content filter stopped it (`FINISH_NOTES` in `src/provider.ts`). Either note counts as content, so a filtered request with no text shows the filter note rather than "No response received from model."

Search models such as Perplexity's cite pages as `[1]`, `[2]` in the text and send the pages only as `source` stream parts, which the gateway provider passes through unchanged (`doStream` in `@ai-sdk/gateway`). `provideLanguageModelChatResponse` collects the `url` sources, keeping the first title for a repeated URL, and when the `finish` part arrives, before any finish note, reports a **Sources** list numbered in arrival order: `[title](<url>)`, or `<url>` without a title. Only `http` and `https` URLs are listed, normalised by `URL`, and the title is escaped so it cannot break the link. `document` sources are left out, since they have no address to open. The list counts as content, and since it is ordinary answer text, VS Code sends it back to the model as part of the assistant message on later turns. Numbering matches the citations only while the provider sends each source once, in citation order, as the AI SDK Perplexity provider does with its `citations`; which other gateway providers send sources is untested. Tests: the source list cases under `provideLanguageModelChatResponse` in `src/provider.test.ts`.

Tools are passed to `streamText` without `execute`, and `jsonSchema` without a `validate` function checks nothing, so `streamText` marks a tool call `invalid` only when the model names a tool that was not offered or sends input that is not valid JSON. It then emits the `tool-call` part, carrying the raw input string when parsing failed, followed by a `tool-error` part. `handleStreamChunk` still hands the call to VS Code, with `{}` in place of any input that is not a plain object, logs the reason at warn, and ignores the `tool-error` that follows, so the chat's tool loop answers the call and the model can retry instead of the answer ending in an `**Error:**`. Whether every consumer answers an unknown tool name with a result the model reads is unknown; the `{}` follows the AI SDK, which makes the same replacement when it builds response messages. A `tool-error` with `providerExecuted` set still reports an error. Tests: the tool call and tool error cases under `handleStreamChunk` in `src/provider.test.ts`.

## Token counting

`provideTokenCount` estimates `ceil(characters / 4)` over the text a message sends: text parts, a tool call's name and JSON input, the text inside tool results, and data parts with a textual MIME type (`tallyPart` in `src/provider.ts`). Each image data part, top level or inside a tool result, adds a fixed `IMAGE_TOKENS` (1600), and every message adds `MESSAGE_OVERHEAD_TOKENS` (4) for role framing. Binary and `cache_control` data parts and thinking parts count as zero. A plain string is `ceil(length / 4)` with no overhead. Until the `provideTokenCount` tests in `src/provider.test.ts` were added it counted top-level text parts only, so tool results, usually the bulk of an agent prompt, counted as zero and VS Code budgeted its prompt against an undercount. It is not a tokenizer, and stays synchronous with no tokenizer dependency.
